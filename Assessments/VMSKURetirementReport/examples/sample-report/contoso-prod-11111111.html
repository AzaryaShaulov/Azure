Cross-Vendor Migration WarningsMoving between Intel and AMD is usually transparent to the operating system, but some workloads need validation first.

Sensitive to a CPU vendor change (Intel ↔ AMD)

  • Licensing: per-core or per-socket licensed software (for example Oracle, some SAP components) may be priced or certified per processor family.
  • Instruction sets: applications compiled for specific extensions (AVX-512, AMX, or vendor-optimised math libraries) must be confirmed on the target processor.
  • Latency-sensitive workloads: real-time, trading or tuned HPC workloads can behave differently with different cache and clock profiles.
  • Infrastructure roles: domain controllers, clustered or appliance VMs: follow the vendor's support statement before changing CPU vendor.

Usually safe to move across vendors

  • Stateless web and API tiers, Linux application servers
  • CI/CD build agents and dev/test environments
  • General Windows workloads and AVD session hosts running productivity apps

How this assessment handles vendors

  • The same CPU vendor is always preferred: Intel → Intel, AMD → AMD, ARM → ARM.
  • A different vendor is proposed only when no same-vendor size passes the mandatory checks. It is flagged CPU Vendor Change Required, loses 20 score points and lowers confidence.

Never cross architecture

  • x64 → Arm64 (Azure Cobalt / Ampere) requires recompiled applications and ARM-compatible OS images. It is never recommended automatically.
  • Test after any resize: run the workload for 24–48 hours and watch CPU patterns and application performance.
